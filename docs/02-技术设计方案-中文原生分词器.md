# 技术设计方案：中文原生分词器（v0.1 草案）

> 阶段 1 核心文档 · 2026-09（目标轮次 2）
> 状态：草案。凡标注「建议默认值」的条目，用户可推翻；标注「待用户拍板」的，需用户确认后才能动工。

## 1. 目标与非目标

**目标**
- 训练一个以中文为第一公民的分词器（词表 + 分词模型 + 代码全部开源）
- 在四个维度上与主流词表做公开量化对比：词元效率、压缩率、字形可解析性、下游语义
- 形成可复现的完整流水线（语料 → 训练 → 评测），任何人可一键重跑

**非目标**
- 本轮不训练语言模型（那是阶段 2 的事）
- 不追求"token 数最小化"（第 1 轮调研已证明：文言文 token 少但推理成本反升，压缩 ≠ 理解）

## 2. 设计原则（不可谈判的底线）

1. **汉字原子性**：任何一个汉字永远不被拆成字节碎片。"人"就是"人"，不会变成 3 个 UTF-8 字节 token。这是对国际模型"中文税"的根上反击。
2. **字形通道不丢失**：部首/部件信息必须被显式保留（第 1 轮调研：字节拆分意外带来的部首聚类红利，我们要主动设计进去，而不是靠巧合）。
3. **中文第一公民**：词表席位分配由中文语料统计决定；英文等其他语言只保留最小应急通道（或实验性地完全去掉）。
4. **字符保真**：归一化策略采用 identity（恒等）——不折叠全角/半角、不改写任何字符。模型看到什么就是什么。（第 4 轮 ADR-009 增补）
5. **可复现**：所有脚本、随机种子、语料版本号入库；评测报告自动生成。

## 3. 六个设计决策点的建议默认值

| # | 决策点 | 建议默认值 | 理由 | 状态 |
|---|---|---|---|---|
| 1 | 基本单位 | 字词混合：全部汉字原子入表 + 高频词按构词统计入表 | 字保证原子性与字形通道；词提升效率与语义完整 | 待用户拍板 |
| 2 | 词表规模 | 两档实验：32k 与 64k | 覆盖全部 CJK 汉字（~27k）后余量给高频词；两档对比"词表大小 vs 下游表现" | 待用户拍板 |
| 3 | 建表算法 | Unigram（SentencePiece）+ 汉字边界预切分 | BPE 的字节合并对汉字有随机性、会拆碎汉字；Unigram 统计更稳 | 建议默认值 |
| 4 | 其他语言通道 | 实验组 A：纯中文（无英文通道）；对照组 B：保留 1k 最小英文通道 | 纯到什么程度本身就是要回答的科学问题，用实验说话 | 建议默认值 |
| 5 | 评测维度 | 四维全做：词元效率 / 压缩率 / 字形可解析性 / 下游语义 | 对齐第 1 轮调研的 STRR 思路，不只看 fertility | 建议默认值 |
| 6 | 训练语料 | 中文维基 + 万卷/WanJuan 抽样 + SkyPile 抽样（详见 §5） | 维基保证质量与可复现；万卷/SkyPile 保证覆盖面 | 待用户拍板 |

## 4. 字形通道的三个可选机制（待实验）

- **方案 B（首推，务实）**：生僻字/低频字按"部件序列"入表（如"龘"→"龍龍龍"），高频字整字入表。既保住字形结构，又不牺牲常用字效率。
- **方案 A（进阶）**：双通道——主词表 + 独立的"部首-部件"侧通道映射表，每个 token 附带部首结构特征（类似 ChineseBERT 的字形特征，但作用在分词层）。
- **方案 C（对照）**：纯整字入表，完全放弃部件级结构，作为实验对照组。

第一版实现做 B + C 对照，A 留作研究扩展。

## 5. 语料选型（第 2 轮调研结果）

| 语料 | 规模 | 许可证 | 用途 |
|---|---|---|---|
| 中文维基百科 dump（zhwiki） | ~1.5B 字符 | CC BY-SA | 主训练语料（质量最高、可复现） |
| 书生·万卷 WanJuan 1.0（上海AI实验室） | 3B+ 文档，多模态 | 开放（研究） | 文本子集抽样：新闻/百科/书籍 |
| SkyPile（昆仑万维） | 150B token | 开放 | 网络文本抽样 |
| MNBVC（超大规模中文语料集） | 目标 40T，持续增长 | 开源项目 | 领域多样性补充（古诗、歌词、台词等） |
| mC4 / CC-100 中文子集 | 数十 GB | 开放 | 备选 |

**训练分词器实际用量**：约 5~10 亿字符即足够词表统计收敛（分词器训练不需要全量喂，抽样 + 去重即可）。大文件放 `data/`（gitignore，不入库），语料清单与抽样脚本入库。

## 6. 流水线设计

```
data/raw/          # 原始语料（下载脚本入库，数据不入库）
  └─ download_*.py
src/
  ├─ preprocess.py     # 清洗：去控制字符、繁简统一（保留繁体实验组？待定）、去重、过滤
  ├─ train_tokenizer.py# Unigram 训练：汉字原子种子 + 词合并；输出 A/B 两个实验组
  ├─ radicals.py       # 部首-部件映射表（基于 Unicode 部首/IDS 数据）
  ├─ tokenize.py       # 分词器封装（加载、编码、解码、词表导出 JSON）
  └─ visualize.py      # 词表可视化（词元频次、覆盖曲线）
eval/
  ├─ benchmark.py      # 四维评测主脚本
  ├─ metrics.py        # token/字、压缩率、fertility、字形可解析性
  ├─ corpora/          # 评测文本集（22 类文本抽样，对齐媒体测试的类目设计）
  └─ report.py         # 自动生成 Markdown/HTML 评测报告
tests/                 # 单元测试（汉字原子性、往返解码、边缘字符）
```

## 7. 评测方法论

**对比对象**（用其官方 tokenizer 权重，仅评测不修改）：
- 英文中心派：GPT（tiktoken/o200k）、Claude、LLaMA 系
- 中文优先派：Qwen、DeepSeek、GLM、Yi

**四个维度**：
1. **词元效率**：同文本集的 token 数比值（中文原生 / 对比对象），分 22 类文本分别报告；
2. **压缩率**：bits/char = token 数 × log2(词表大小) / 中文字符数（信息论口径，越低越省；注：原"字节比"定义对任意划分恒为 1，已废弃）；
3. **字形可解析性**：生僻字是否被拆碎为字节、部首在 token 层面是否可恢复（新指标，我们自己定义并开源）；
4. **下游语义**：下游任务代理（掩码语言建模困惑度，需等阶段 2 的小模型；本轮先出指标定义与基线脚本，实验留待阶段 2）。

**评测文本集**：现代汉语（新闻/百科/对话/技术文档）、文言文、古诗、医学/专业文献、混合中英文、生僻字压力测试。

## 8. 里程碑

- **M0 环境**（下一步）：安装 Python 3.12 + git + sentencepiece/tokenizers/jieba；仓库初始化并推到 GitHub
- **M1 数据**：语料下载脚本 + 清洗 + 抽样（产出 ~5 亿字符训练集）
- **M2 训练**：A/B 两组词表 + C 对照；汉字原子性单测通过
- **M3 评测**：四维对比报告自动生成；与 Qwen/DeepSeek/GPT/Claude 的完整对比表
- **M4 发布**：开源（词表、代码、报告、复现指南）；许可证 Apache-2.0

## 9. 风险与对策

| 风险 | 对策 |
|---|---|
| 字形红利丢失（整字 token 封装部首信息） | 方案 B 的部件序列设计 + 评测维度 3 显式测量 |
| 词表过大导致小模型欠拟合 | 32k 与 64k 双档实验，用数据说话 |
| 纯中文通道遇到英文/代码输入 | 对照实验组 B（最小英文通道）量化代价 |
| 语料版权与合规 | 只用明确开放的语料 + 记录来源与许可证 |
